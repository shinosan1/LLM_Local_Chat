# LLM Local Chat

ローカルLLM（llama.cpp）＋ Whisper音声認識＋ Windows SAPIを組み合わせた日本語AIチャットアプリです。  
**必要な依存ライブラリとモデルを取得済みの場合、推論・音声認識・音声合成・会話処理はローカルで実行されます。Biologと家計簿API連携は、別プロセスのローカルHTTP APIを任意で利用します。**

ローカル処理を重視した構成です。機密情報を扱う業務環境へ導入する場合は、端末のアクセス制御、Windowsユーザープロファイル、ディスク暗号化、Dockerポート、依存ライブラリ、バックアップ方法を含め、組織の情報セキュリティ担当者による事前評価を行ってください。

## 主な機能

- ストリーミング表示によるリアルタイム応答
- PyAudio + RMS-VAD + Whisper による常駐音声認識
- Windows SAPI5（win32comによる直接制御）のTTS読み上げ
- アバターウィンドウ（瞬き・口パクアニメーション）
- 会話の要約メモリ（長期会話対応）
- チャット履歴の保存・読み込み・検索
- `chat_settings.json`によるsystem prompt・persona・応答言語等のパーソナライズ
- TXT / MD / JSON / CSVとPNG / JPEGのチャット単位の永続添付
- ゲストモード（`chat_logs/`への履歴保存なし）
- ダークテーマUI
- **Biolog健康記録連携** — 💪ボタンで計測値・食事・活動内容・メモを入力し、確認後にBiolog APIへPOST（v1.1.0）
- **家計簿API連携（オプション）** — ユーザー入力から最大10件の取引候補を生成し、1件ずつ確認したうえで、別途用意したローカルの`kakeibo-bridge` APIへ1件ずつPOSTします。家計簿アプリ、家計簿DB、`kakeibo-bridge`サーバー実装は本リポジトリに含まれません
- **VRAM安全フィルタ** — LLM・Whisper 同時動作時のVRAM枯渇によるクラッシュを確率的に削減（v1.2.0）
- **LLM GPUオフロード切替** — 自動・Full GPU・約75%・約50%・約25%・CPUを設定画面から選び、アプリを再起動せずモデルを安全に再読み込みします

## v1.8.0 チャット単位の保存済み添付

リリース日: 2026-08-27

TXT / MD / JSON / CSVとPNG / JPEGは、添付時点のコピーをチャットへ紐づけて保存します。同じチャットでは後続質問・チャット切替・アプリ再起動後も再添付せず参照できます。履歴JSONには復元用メタデータだけを保存し、本文・画像本体・元ファイル絶対パスは埋め込みません。

設定の「保存済み添付ファイル」では、個別削除と全チャット対象の一括削除、総件数・合計容量を確認できます。保存領域はユーザー単位に分離されないため、共有環境での一括削除は同じ保存領域を使う他利用者の添付にも影響し得ます。

`system_prompt`等のinline設定と外部promptは併用できます。本文なしで添付だけを送信する操作、同名・別内容の複数添付にも対応しました。

## v1.7.1 不具合修正

この節は、LLM Local Chat側の家計簿API連携クライアントにおける候補生成・検証・確認・送信処理の修正です。実際の台帳登録には別途起動した`kakeibo-bridge` APIが必要で、家計簿アプリ、家計簿DB、bridgeサーバーは本リポジトリに含まれません。

### LLM GPUオフロードの再起動不要切替

生成設定では、LLM GPUオフロードの希望モードを`自動`・`Full GPU`・`約75%`・
`約50%`・`約25%`・`CPU`から選択できます。変更時はチャットやアプリを終了せず、
旧モデルを解放してから新しい配置でバックグラウンド再読み込みします。

希望モードとは別に、最後に実際にロード成功したGPUオフロード率・配置レイヤー数・
Full/Partial/CPUを読み取り専用で表示します。`自動`では推論直前に最低予約量を
下回った場合だけ現在より低い配置へ自動downshiftし、同じ入力を1回だけ継続します。
推論ごとの自動upshiftは行わず、上位配置の再検討は起動・通常のモデル再読み込み・
設定画面の「GPU配置を再評価」で行います。

### 家計簿の日付入力に日本語形式を追加

家計簿の日付は、従来の `YYYY/MM/DD`、`YYYY-MM-DD`、`M/D` に加えて、
`M月D日` と `YYYY年M月D日` もユーザー原文から機械抽出します。全角数字にも対応します。

| 入力例 | 登録候補の日付 |
|---|---|
| `8月22日セリア1130円` | 実行年を補った `2026-08-22`（実行年が2026年の場合） |
| `８月２２日セリア１１３０円` | 同上 |
| `2026年8月22日セリア1130円` | `2026-08-22` |
| `２０２６年８月２２日セリア１１３０円` | `2026-08-22` |

実在しない日付は明示日付として採用しません。無効な年付き表現の内部を年なし形式として
再解釈することもありません。例えば、実行年が閏年でも `2025年2月29日` を
実行年の `2月29日` として採用せず、日付なしの場合と同じく実行日へフォールバックします。

「昨日」「一昨日」「先週」などの自然言語相対日付には対応していません。
日付は引き続きLLM出力ではなくユーザー原文から決定し、確認画面で修正できます。

### 日付直後の金額入力を修正

`8/20 1603円`、`2026/8/20 1603円`、`2026-08-20 1603円`のように、
日付の直後へ空白を置いて正常な金額を入力した場合も登録候補として扱います。
`1 603円`や`12 000円`のように金額の数字列自体が空白で分断された表記は、
従来どおり不正形式として拒否します。

### 金額直後の日本語日付入力を修正

`2170円8月18日`や`1130円2026年8月22日`のように、金額の直後へ
`M月D日` / `YYYY年M月D日`が続く自然入力も正しく扱います。数字列の単なる連結は
許可せず、実在しない月日や`100円50`のような表記は金額候補として採用しません。

### 複数取引のsource_text空白差を安全に復元

複数取引でLLMが `source_text` 内の半角スペースまたは全角スペースだけを
削除・追加・置換した場合、完全一致を先に試したうえで、原文上の位置が一意に
確定できるときだけ元の原文断片へ復元します。最終候補にはLLMが整形した文字列ではなく、
対応する原文の実スライスを使用します。

句読点、金額カンマ、数字、日付、店名、改行などの差は無視しません。
空白を除いた一致位置が複数ある場合や断片同士が重なる場合も、従来どおり入力全体を拒否します。

## v1.7.0の主な改善

### LLM Local Chat側の家計簿API連携：複数取引対応

1回の入力から**最大10件の取引候補を生成**できるようになりました。

これはLLM Local Chat側の候補生成・確認・API送信処理の改善です。実際の台帳登録には、別途用意したローカルの`kakeibo-bridge` APIが必要です。

**一括登録ではありません。** 「1取引 = 1確認 = 1 POST」という安全境界はそのままで、変わったのは入口だけです。候補は1件ずつ確認し、`kakeibo-bridge` APIへ1件ずつPOSTします。

```text
入力: スーパーで2000円、コンビニで500円、薬局で1200円

  (1 / 3) スーパー  2,000円  → 確認 → POST #1
  (2 / 3) コンビニ    500円  → 確認 → POST #2
  (3 / 3) 薬局      1,200円  → 確認 → POST #3
```

| 項目 | 動作 |
|---|---|
| 上限 | 10件（`MAX_KAKEIBO_TRANSACTIONS_PER_INPUT`） |
| 11件以上 | **入力全体を拒否**（確認画面0件・POST 0件）。先頭10件だけ処理する部分成功は行いません |
| 金額・日付 | 従来どおり**LLM出力を最終値にせず**、各取引の原文断片から機械抽出します |
| 確認 | 複数のときはタイトルへ `(2 / 3)` を表示。「この取引をスキップ」と「残りを中止」を分けています |
| 送信 | **直列**。前のPOSTの完了を待ってから次の確認画面を開きます（並列送信はしません） |
| 途中失敗 | 残りの候補を処理せず停止します。このクライアントからPOST済みの取引は取り消しません |
| 1件だけの入力 | 従来どおりの動作・従来どおりの確認画面です |

LLMが返す取引ごとの原文断片（`source_text`）は信用せず、**原文に実在すること・空でないこと・範囲が重複しないこと・原文順に並べられること**をコード側で検証します。原文に無い文言をLLMが生成した場合は候補になりません。

1つの断片に有効な金額候補が複数あり、1取引なのか内訳なのか判断できない場合は、推測せず入力全体を拒否します。

さらに、次の場合は**推測せず入力全体を拒否**します（意図しない部分送信を防ぐため）。

| 状況 | 例 | 動作 |
|---|---|---|
| LLMが取引を取りこぼした | 原文に3取引あるのにLLMが2件しか返さない | 全体拒否。原文の金額をすべての断片が覆っているかを確認します |
| 金額だけの断片 | 「スーパーで2000円と500円」を「スーパーで2000円」「500円」へ分割 | 全体拒否。同一文脈内の複数金額を人工的に切り分けたものは受理しません |
| 日付が一意に決まらない | 「8/16 スーパーで2000円、8/17 コンビニで500円、薬局で1200円」 | 全体拒否。薬局がどちらの日付か確定できません |

日付は、原文全体の明示日付が**ちょうど1種類のときだけ**、日付を持たない取引へ適用します。「8/16 スーパーで2000円、コンビニで500円」なら両方 8/16 です。

確認・POSTシーケンスが進行中の間は、**キーボード入力・音声入力とも新しい送信を開始しません**（`Controller.is_busy()`）。完了・スキップ・中止・エラーのいずれでも解除されます。

音声入力とキーボード入力は同じ経路を通るため、どちらでも同じ処理になります。

## v1.6.1の主な改善

### 家計簿モードの日付解析

原文に年付きの日付が明示されている場合、その日付をそのまま登録候補に使うよう修正しました。

```text
入力: 2026/08/16 テスト店にて日用品2000円分買う
　　　　　↓
日付: 2026-08-16
```

v1.6.0以前は、`2026/08/16` と `2026-08-16` のどちらの形式も日付として認識されず、常に実行日へフォールバックしていました。

対応する日付形式は次のとおりです。

| 入力形式 | 採用される日付 |
|---|---|
| `2026/08/16` | 原文の年月日をそのまま使用 |
| `2026-08-16` | 同上（`/` 形式と同じ結果） |
| `2026年8月16日` | 原文の年月日をそのまま使用 |
| `7/17` | 実行年を補って使用（従来どおり） |
| `7月17日` | 実行年を補って使用 |
| 日付表現なし | 実行日を使用（従来どおり） |

実在しない暦日（`2026/02/30`・`2026年2月30日`）、範囲外の月（`2026/13/01`）、
区切り文字の混在（`2026/08-16`）は日付として扱わず、実行日へフォールバックします。
無効な年付き日本語日付の内部を、年なしの月日として再解釈することはありません。

日付はLLMの出力を使わず、ユーザー原文からの機械抽出だけで決定します（金額と同じ方針）。確認画面での手入力による修正も従来どおり可能です。

## v1.5系の主な改善

### 暗号化インポート／エクスポート

別PCや別のWindowsユーザー環境へ会話履歴を移行するため、パスフレーズ付きの暗号化形式`.shiro-export`を追加しました。

通常の会話履歴は、これまでどおり現在のWindowsユーザーに紐づくDPAPIで暗号化して保存します。`.shiro-export`は、DPAPI履歴を別環境へ移すための持ち運び用形式です。

暗号化には以下を使用します。

* scryptによるパスフレーズからの鍵導出
* AES-256-GCMによる認証付き暗号化
* 暗号設定を含む外側ヘッダーのAAD認証
* 毎回新しく生成されるsaltとnonce

パスフレーズ、暗号鍵、復号済みの会話履歴は、設定ファイルやログへ保存しません。暗号化・復号時にも平文の一時ファイルは作成しません。

### エクスポート対象

暗号化エクスポートの対象は、DPAPIでディスクへ保存済みの会話履歴だけです。

以下はエクスポートできません。

* ゲストモードの会話
* まだ保存されていない会話
* 保存後にメモリ上で追加・変更された未保存部分
* 保存済み添付の実体と添付メタデータ

`.shiro-export`をインポートしても添付は復元されません。この形式は会話履歴の持ち運び用であり、添付ファイルのバックアップではありません。

「現在の会話のみ」を選択した場合も、保存済みの履歴をディスクから読み直してエクスポートします。

### インポート処理

`.shiro-export`をインポートすると、パスフレーズで復号した後、現在のWindowsユーザー用DPAPIで再暗号化して`chat_logs`へ保存します。

保存前に以下を確認します。

* ファイル形式とバージョン
* scrypt、salt、nonce、AES-GCM設定
* 暗号文の改ざん
* 復号後の履歴形式
* 会話件数、文字数、入れ子、ファイルサイズなどの上限
* 既存履歴との重複
* 履歴の保存期間

すべての履歴を検証してから保存を開始し、通常の書き込みエラーが発生した場合は、今回追加した履歴を巻き戻します。既存の履歴は変更・上書きしません。

重複する会話は、スキップするか複製としてインポートするかを選択できます。

### 注意事項

* `.shiro-export`のパスフレーズを忘れた場合、履歴を復旧できません。
* 弱いパスフレーズは、暗号化ファイルを取得した第三者によるオフライン解析を受ける可能性があります。
* 暗号化ファイルとパスフレーズを同じ場所へ保存しないでください。
* 通常のDPAPI履歴は、別PCや別のWindowsユーザーでは復号できない可能性があります。
* クラウドストレージなど保存先自体の安全性を、本アプリが保証するものではありません。

### v1.5.2の操作画面

v1.5.0では、暗号化エクスポート時にゲスト会話や未保存会話が含まれる可能性がありました。

v1.5.1ではエクスポート経路を修正し、DPAPIで保存済みの履歴だけをディスクから読み込んで出力するように変更しました。v1.5.2では、対象範囲を曖昧な「はい／いいえ」で選ばず、ファイルメニューから次のどちらかを直接選択します。

* 現在の保存済み会話をエクスポート
* 保存済みの全会話をエクスポート

保存先とパスフレーズは同じ画面で入力します。インポートもファイルとパスフレーズを同じ画面で指定し、重複する会話は「重複をスキップ（推奨）」「重複もコピー」「キャンセル」の明示的なボタンで選びます。

エクスポート先は`.shiro-export`ファイルに限定されます。上書き確認後、実際の書込み前に出力先の作成・削除・変更を検知した場合は、安全のため書込みを中止します。この確認は意図しない上書きの可能性を下げるためのbest-effort対策であり、別プロセスとの完全な排他制御を保証するものではありません。

重複確認画面の追加予定件数は確認時点の値です。確認後に既存履歴が変化した場合があるため、完了画面に表示される実際の追加件数とスキップ件数を最終結果として確認してください。

## v1.4.2の履歴保護

- `chat_logs/`の会話本文・タイトル・要約を、現在のWindowsユーザー用DPAPIで必須暗号化
- v1.4.1以前の平文履歴は、初回起動時の確認後に検証付きで原子的に移行
- 保存期間を無期限・30日・90日・180日・365日から選択可能（既定は無期限、90日を推奨）
- DPAPI保存に失敗した場合は平文へフォールバックせず、UIへ通知
- 平文テキスト保存を廃止し、別環境へ移せるパスフレーズ付き暗号化エクスポートを提供

暗号化後の履歴はv1.4.1以前では読み込めません。DPAPIはWindowsユーザープロファイルと環境に依存するため、OS再インストール、ユーザープロファイル消失、一部のパスワード管理操作などで復号できなくなる場合があります。

### 起動できない場合の復旧手順

会話履歴の復号・形式確認・移行に失敗した場合、Shiroは履歴を自動削除・自動移動せず、通常起動を中止します。

1. 元のWindowsユーザーと元のPC環境で起動しているか確認します。DPAPI暗号文は別ユーザーや別環境では復号できない場合があります。
2. 旧版を含むすべてのShiroを終了し、`chat_logs/`と対象ファイルのバックアップを確保します。バックアップはアクセス制限された場所に保存し、公開リポジトリや共有クラウドへ置かないでください。
3. 破損・未対応と表示されたファイルがある場合は、削除せず、`chat_logs/`外の安全な非公開フォルダへ手動で退避してから再起動します。退避した履歴は一覧に表示されなくなります。
4. `.history_migration.lock`が残っている場合は、すべてのShiroが終了していることを確認した場合に限り、`chat_logs/.history_migration.lock`を手動で削除して再起動します。Shiroの実行中は削除しないでください。
5. 「Windows DPAPIを利用できません」と表示された場合は、同梱の依存関係と`pywin32`が利用できるPython環境で起動してください。

初回移行中は旧版Shiroを同時起動しないでください。ロックファイルはv1.4.2同士の移行を調整するもので、旧版による平文履歴の新規保存までは防げません。

暗号化後の履歴はv1.4.1以前では読み込めません。別PC・別Windowsユーザーへ移す場合は、ファイルメニューの「暗号化エクスポート」を使用してください。

### 暗号化インポート／エクスポート

`.shiro-export`は、scryptでパスフレーズから鍵を導出し、AES-256-GCMで会話履歴とメタデータを認証付き暗号化する持ち運び用形式です。通常の`chat_logs/`はWindows DPAPI、持ち運び用ファイルはパスフレーズ暗号化という役割分担です。

- パスフレーズは設定・履歴・ログへ保存されません。紛失した場合は復元できません
- 出力は人間が直接読めるテキストではありません
- 復号した平文を一時ファイルへ保存せず、メモリ内で検証します
- インポート後は現在のWindowsユーザー用DPAPIで再暗号化します
- 暗号化ファイルとパスフレーズを同じ場所へ保管しないでください
- Python上の平文・鍵をメモリから完全消去できるとは保証しません
- 通常の書込例外では追加ファイルを巻き戻しますが、停電・OS停止に対する完全なトランザクション保証はありません
- 既存の平文`.txt`はインポート対象ではなく、アプリが自動削除することもありません

## VRAM安全フィルタ（v1.2.0）

LLM（Gemma 4 E4B、総8B／有効4B）とWhisper mediumを同一GPUで動かす際のVRAM競合を緩和します。

### 設計思想

**「VRAMを管理する」ではなく「VRAMから逃げる」** — OOMの完全防止は不可能です。
この機能は「クラッシュではなく性能劣化」で済ませることを目標としています。

### 自動フォールバックの仕組み

| 状況 | 動作 |
|---|---|
| LLMロード前の空き容量がGGUFサイズ+予約領域以上 | `n_gpu_layers=-1`で全層GPUオフロードを要求 |
| Full条件未満でGGUF総レイヤー数を取得できる | モデルサイズの概算と予約領域から約75%→50%→25%を順に検討 |
| CUDA非対応、GPU情報取得不能、partial条件も満たさない | `n_gpu_layers=0`（CPU実行）にフォールバック |
| GPUロード時の明示的なVRAM不足、またはロード後の最低予約量不足 | 安全に解放して一段低い候補を検討 |
| Whisperモード`auto`・空き4096MB以上 | GPU版mediumを使用 |
| Whisperモード`auto`・空き2048〜4095MB | GPU版smallを使用 |
| Whisperモード`auto`・空き2048MB未満 | CPU版smallのみで運用 |
| 推論時の実空き容量 < 予約領域（512MBまたは総容量の6%） | `自動`モードでは旧LLMを解放後、現在より低いoffloadへ再配置して同じ入力を1回だけ継続。安全に再配置できない場合だけエラー表示 |
| 推論時の実空き容量 512〜1024MB | `max_tokens` を25%に削減 |
| 推論時の実空き容量 1024〜1536MB | `max_tokens` を50%に削減 |
| GPU使用率 > 88% | Whisper を CPU に切替（ヒステリシス付き） |
| GPU版Whisperロード済みでGPU使用率 < 70% | Whisper を GPU に切替復帰 |

### DEBUGログの見方

```
.\.venv\Scripts\python.exe -c "import logging; logging.basicConfig(level=logging.DEBUG); exec(open('LLM_Local_Chat.py').read())"
```

| プレフィックス | 内容 |
|---|---|
| `[Monitor]` | VRAM瞬時値・GPU% の収集ログ |
| `[GPU]` | CUDAバックエンド対応と要求したGPUレイヤー数 |
| `[VRAM]` | LLMロード前後と推論直前の総量・使用量・実空き容量 |
| `[Whisper]` | GPU→CPU / CPU→GPU 切替ログ |
| `[Whisper]` | CPU/GPUモデルのロード・スキップ理由 |

### 既知の限界

- pynvml/nvidia-smi はアロケータ後のスナップショット（TOCTOU あり）
- 他プロセスの使用分も総VRAM使用量には反映されますが、プロセス別内訳やロード後の急な確保までは予測できません
- 確率的削減が目的であり、OOMの完全防止は保証しない

Whisper実行モードは設定画面で`自動`・`GPU small`・`GPU medium`・`CPU small`から選択でき、次回起動時に反映されます。手動GPU指定でも安全な空き容量を満たさない場合はCPU smallへフォールバックします。

生成設定では、希望する**LLM GPUオフロード モード**を選択し、アプリを再起動せず反映できます。実際にロード成功した**GPUオフロード率と配置レイヤー数**（例: `76%（32 / 42層・Partial GPU・自動選択）`）は別の読み取り専用欄で確認できます。これはLLMレイヤーの配置割合であり、WindowsのGPU使用率ではありません。希望モードだけを設定ファイルへ保存し、実配置のruntime stateは保存しません。

## ⚠️ 必ずお読みください

### 音声入力について
音声入力は周囲の音（テレビ・エアコン・会話等）を拾うことがあります。  
これにより意図しない発話が送信される**ハルシネーション**が発生する場合があります。

**対処方法：**
- メニューの「設定」から**音声検出感度（RMS閾値）の数値を上げる**ことで改善できます
- デフォルト値は150です。200〜300程度に上げると誤検知が減少します
- 数値が大きいほど感度が低くなります（静かな環境では小さい値を推奨）
- 使用しないときはマイクボタンをクリックしてOFFにしてください

### 免責事項
- 本アプリはAIの回答精度を保証しません
- 音声認識の誤認識・ハルシネーションにより意図しない操作が行われる場合があります
- 重要な情報は必ずご自身で確認してください

### 6. モデルを設定する

`chat_settings.json`がない場合も、アプリはコード既定値で起動を試みます。既定のモデルが見つからない場合は読込エラーが表示されますが、メイン画面の「ファイル」→「設定」を開き、「参照」ボタンから用意したGGUFモデルを選択して適用できます。保存した設定は`chat_settings.json`へ記録されます。

起動前に手動設定したい場合だけ、`chat_settings.json.example`を`chat_settings.json`へコピーし、`model_path`などを編集してください。

パーソナライズとVisionは、設定画面ではなく`chat_settings.json`で設定します。既存の設定ファイルに次のキーがなくても従来どおり起動します。

```json
{
  "system_prompt": "",
  "user_personalization": "",
  "response_language": "回答は必ず日本語のみで行ってください。",
  "reasoning_visibility_instruction": "内部の思考過程、分析、推論、計画は表示せず、ユーザーに見せる最終回答だけを出力してください。",
  "external_prompt_files": {
    "system_prompt": "prompts/system.md",
    "user_personalization": "",
    "user_profile": "prompts/profile.txt",
    "instructions": []
  },
  "vision_enabled": false,
  "vision_handler": "gemma4",
  "vision_projector_path": ""
}
```

外部promptはUTF-8の`.txt` / `.md`に対応し、相対パスはアプリ配置フォルダ基準です。inline system → external system → inline personalization → external personalization → response language → reasoning visibility → external profile/instructionsの順で併用し、完全に同一の文章と同一ファイルだけを重複挿入しません。外部promptの欠損・形式・文字コード・サイズのエラーは警告を表示し、inline設定を含む読める設定だけで起動を継続します。

Visionを使う場合は、現在の`llama-cpp-python 0.3.34`で利用できる`gemma4`または`llava15`を指定し、対象モデルに対応するprojector / mmproj GGUFを`vision_projector_path`へ設定してください。`vision_enabled`の既定値は`false`です。

## 使い方

### 基本操作

起動するとメインウィンドウとアバターウィンドウが開きます。  
ステータスバーが「✅ 待機中」になったらチャット可能です。

テキスト入力欄にメッセージを入力して `Enter` キーまたは「送信」ボタンで送信します。  
`Shift + Enter` で改行できます。

### ファイル添付

入力欄上の「📎 ファイルを添付」から、TXT / MD / JSON / CSVまたはPNG / JPEGを選択できます。本文あり・添付あり、本文だけ、添付だけのいずれも送信できます。本文も添付もない場合は送信しません。添付は通常チャットだけで使用でき、最大8件、画像はそのうち1枚までです。同名でも内容が異なるファイルは内部IDで区別し、`data.csv`、`data.csv (2)`のように表示します。

添付時点の内容は`chat_logs/attachments/<session-id>/`以下のアプリ管理領域へ、元ファイル名ではなく内部IDを使ってコピーします。送信後も「チャット添付: ファイル名」の表示が残り、「続けてください」などの後続質問へ同じ内容を1ターン内で重複させず再投入します。新しいチャットを開始しても元チャットの添付は削除されず、別チャットを開けばそのチャット固有の添付へ切り替わります。保存済みチャットを再読込したときとアプリ再起動後にも復元します。

保存済み添付は元ファイルとは別コピーです。元ファイルを編集・移動・改名・削除しても自動更新されません。最新版を使う場合は、現在チャットの古い添付を解除して再添付してください。添付は重要ファイルのバックアップシステムではなく、アプリ内添付を唯一の保存場所として利用しないでください。

入力欄の「添付解除」は、確認ダイアログで同意した場合に、現在のチャットに紐づく**すべての添付**と対応するアプリ管理領域のコピーを削除します。会話本文とAI回答、元ファイル、別チャットの添付は削除しません。チャット自体を削除した場合は、そのチャット専用の添付も内部ID・セッションIDで削除します。削除した添付は過去チャットから再参照できず、アプリによる復元は保証されません。

保存管理の操作経路は、`ファイル → 設定 → 保存済み添付ファイル → 選択した添付を削除`または`保存済み添付ファイルをすべて削除`です。一覧ではファイル名、種類、サイズ、紐づくチャット、状態、総件数、合計容量を確認できます。一括削除は**現在のアプリ保存領域で管理される全チャットの保存済み添付**が対象で、通常の会話履歴は残ります。部分失敗時は成功・失敗・スキップ・再試行待ち件数を表示し、完了していないのに「すべて削除しました」とは表示しません。

履歴JSONへ直接保存するのは、内部ID、basename、種類、サイズ、SHA-256等の復元用メタデータだけです。元ファイル絶対パス、TXT / MD / JSON / CSV本文、画像bytes、base64、data URIは埋め込みません。ただし、LLMが添付内容やファイル名を回答へ引用・要約した場合、その**AI回答は通常の会話履歴として保存**され、後の要約メモリにも含まれる可能性があります。

本アプリはユーザーアカウント単位の添付分離・認証・権限管理を提供しません。同じWindowsアカウント、同一PC、共有フォルダ等で同じアプリデータ保存領域を複数人が使用する場合、一括削除はその保存領域を利用する他のユーザーを含む全チャット添付へ影響する可能性があります。Windowsの別ユーザーであっても同じ保存先を共有する場合は、ユーザー単位の保護を保証しません。ローカルLLMであることだけで、PCへの不正アクセス、マルウェア、同一アカウントの別利用者、アクセス権を持つプロセスから完全に安全になるわけではありません。

個人情報、業務機密、パスワード、APIキー、アクセストークン、秘密鍵等を含むファイルは不用意に添付しないでください。TXT / MD / JSON / CSV内のPowerShell、shell、Python、JavaScript等は自動実行せず、LLMへの入力データとして扱います。一方、文書内の「これまでの指示を無視してください」のような文章がprompt injectionとして回答へ影響する可能性はあります。外部から取得した文書を信頼できる命令として扱わず、生成結果を確認せず重要な操作へ利用しないでください。拡張子、UTF-8、ファイルサイズ、画像形式・画素数の検査は異常入力の影響を抑える制限であり、ファイルや回答の安全性を完全には保証しません。

テキストは1ファイル1MiB、画像は1ファイル10MiBかつ16メガピクセル以下です。上限超過やUTF-8で読めないテキストは切り捨てずに拒否します。添付がある間は、system prompt・要約・全会話履歴・添付・新規入力・応答予約を合わせてcontextへ収まらない場合、履歴を黙って省略せず警告します。画像入力では4,096画像トークンを事前予約しますが、モデル固有の実トークン数を送信前に完全保証できないため、実行時にcontext超過として拒否される場合があります。

保存済み添付はアプリ終了後も残るため、画像や多数の添付を使い続けるとディスク使用量が増えます。自動期限削除、自動容量削減、ごみ箱、自動バックアップ、添付暗号化は提供しません。設定画面の件数・合計容量・個別削除・一括削除を使って管理してください。実体欠損、読込不能、サイズ不一致、保存済みSHA-256との不一致を検出した添付はLLMへ渡さず、警告します。

`.shiro-export`には添付実体も添付メタデータも含まれません。インポート後のチャットへ添付は復元されないため、`.shiro-export`を添付ファイルのバックアップとして使用しないでください。

### 音声入力

コード上の既定値と`chat_settings.json.example`では、起動時のマイク・TTS読み上げはともに**OFF**です。「ファイル」→「設定」で次回起動時の状態を変更できます。
マイクボタンをクリックするとONになります。  
ONの状態で一定以上の音量を検知すると自動的に録音を開始し、Whisperで文字起こしして送信します。  
再度クリックするとOFFに戻ります。

> 起動時マイクを有効にする設定とWhisper実行モードは、次回起動時に反映されます。初回のWhisperダウンロード・ロードには時間がかかる場合があります。
> TTS読み上げ中はハウリング防止のため音声入力が自動的に抑制されます。

### TTS（読み上げ）

AIの返答をWindows SAPIで読み上げます。起動時はOFFがデフォルトです。  
メニューからTTSのON/OFFを切り替えられます。  
読み上げ中は「停止」ボタンで中断できます（タイミングによっては中断できない場合があります）。

### 健康記録モード（Biolog連携） — v1.1.0

💪ボタンをクリックすると健康記録モードがONになります。  
このモードでは、計測値・食事・活動内容・メモを話しかけると、確認後にBiolog APIへデータをPOSTします。食事ログ、行動ログ、メモだけの登録にも対応します。

**入力例：**
```
体重65kg、体脂肪20%、朝はオートミールを食べた
```

**動作結果：**
- チャットに「✅ Biolog記録: 2026-05-06 体重 65.0kg 食事:朝はオートミールを食べた」と表示
- Biologの健康記録へ保存

**事前準備：**
Biolog側の文書とComposeを確認してAPIを起動し、LLM Local Chatを実行するPCからヘルスチェックへ接続できることを確認してください。
標準ComposeではBiolog APIを`127.0.0.1:8766`に限定して公開します。

```powershell
curl http://localhost:8766/api/health/health
```

**環境変数でエンドポイントを変更できます：**
```powershell
$env:BIOLOG_URL = "http://localhost:8766"  # デフォルト
.\.venv\Scripts\python.exe LLM_Local_Chat.py
```

> 計測値・食事ログ・行動ログ・メモがすべて空の場合だけ送信しません。`食事ログ`・`行動ログ`・`メモ`を明示した入力は、ユーザー原文から決定的に解析されます。

### ゲストモード

「ゲストモード: OFF」ボタンをクリックするとゲストモードがONになります。  
ゲストモードがONのとき、会話履歴は`chat_logs/`へ自動保存されず、ゲスト会話を暗号化エクスポートすることもできません。ただし、実行中のメモリ、標準出力やOS側のログ、連携先APIへ送信したデータまで消去・保護する機能ではありません。
プライベートな会話や一時的な用途に使用してください。  
再度クリックすると通常モードに戻り、新しいセッションが開始されます。

### チャット履歴

左ペインに過去の会話一覧が表示されます。クリックで読み込めます。  
上部の検索欄でタイトル・要約の部分一致検索ができます。  
右クリックで個別削除が可能です。  
履歴はアプリ配置フォルダ内の`chat_logs/`へ、DPAPI暗号化されたJSONエンベロープとして保存されます。ファイル名、件数、サイズ、更新日時は暗号化されません。
設定画面で保存期間を選択できます。有限期間を初めて適用するときは削除候補件数を表示し、確認後すぐに削除します。外部バックアップは自動削除されないため、バックアップ側の保持期間も別途管理してください。

### 要約メモリ

一定ターン数ごとに会話の要約が自動生成され、次の応答に注入されます。  
長期会話でもコンテキストが維持されやすくなっています。

### 設定

メニューから「ファイル」→「設定」を開くと、以下の項目を変更できます。

| 項目 | 内容 | 推奨値 / アドバイス |
| :--- | :--- | :--- |
| **モデルファイル** | 使用する GGUF モデルのパスを指定します。 | 「参照」ボタンから任意の場所にある対応GGUFファイルを選択できます。 |
| **LLM GPUオフロード モード** | `自動`・`Full GPU`・`約75%`・`約50%`・`約25%`・`CPU`から希望配置を選びます。 | 保存後、旧モデルを解放してからバックグラウンドで再読み込みし、再起動なしで反映します。安全条件を満たさない上位配置は下位へフォールバックします。 |
| **現在の実行状態** | 実際にロード成功したGPUオフロード率・配置レイヤー数・Full/Partial/CPUを表示します。 | 読み取り専用です。「GPU配置を再評価」は`自動`モードの配置を現在のVRAMから選び直します。 |

## よくある質問

**Q. OllamaやLM Studioを使わないのはなぜですか？**  
A. llama.cppをPythonバインディング（llama-cpp-python）から直接呼び出し、LLM推論をローカルで実行するためです。必要な依存ライブラリとモデルを取得済みで、オプションのBiolog・家計簿API連携も別プロセスのローカルAPIへ限定した構成では、通常の会話処理に外部のLLMサービスを使用しません。セットアップ、モデル取得、外部リンクの閲覧にはインターネット接続が必要です。

**Q. CPUだけでも動きますか？**  
A. CPU実行へフォールバックできます。CPU専用PCでは、セットアップ時に`requirements-cpu.txt`を使用してください。応答速度はモデルサイズ、量子化形式、CPU、メモリ帯域、コンテキスト長などに大きく依存し、実用的な速度になるとは一律に保証できません。

**Q. Whisperのモデルは自動でダウンロードされますか？**  
A. 起動時マイクを有効にした場合、初回ロード時にWhisperモデルが自動的にダウンロードされます。マイク無効時は、TTSが有効でもWhisperをロードしません。

**Q. TTSには何を使用していますか？**
A. `win32com.client.Dispatch("SAPI.SpVoice")` により、Windows SAPI5をワーカースレッドから直接制御しています。

本アプリを業務環境に導入される際は、以下のセキュリティ上の特性を情報セキュリティ担当者と共有・確認してください。

脆弱性を報告する場合は[SECURITY.md](SECURITY.md)を確認し、詳細を公開Issueへ投稿しないでください。

### セキュリティ上の特性

**確認済みの範囲**
- LLM推論、Whisper音声認識、Windows SAPI5による音声合成はローカルプロセスで実行されます
- 現在のアプリコードでは、外部のLLM APIへ会話内容を送信する処理は確認できません
- Biolog・家計簿API連携は別プロセスのHTTP APIを使用します。現在のアプリコードでは接続先をループバックアドレスに制限し、環境プロキシを使用せずに接続します。家計簿アプリ、DB、`kakeibo-bridge`サーバーは本リポジトリに含まれず、実際に利用できるかどうかは別途用意したローカルAPIの稼働・ネットワーク設定にも依存します

> **⚠️ 使用するモデルについての注意：**  
> GGUFモデルファイル自体が独立して通信や攻撃を行うものではありません。ただし、信頼できない、または破損したファイルがモデル読み込みライブラリの脆弱性を突く可能性があります。信頼できる配布元から取得し、`llama.cpp`および`llama-cpp-python`を定期的に更新してください。モデルの仕様・ライセンスも確認してください。

**導入・運営前に確認すべき点**
- 会話履歴はWindows DPAPIの現在ユーザースコープで暗号化されます。暗号化は同一Windowsユーザーとして動作する別プロセスやマルウェア、実行中メモリ、画面、クリップボード、標準出力を保護しません
- 暗号文は原則として同じWindowsユーザープロファイルと当該Windows環境に依存します。OS再インストール、プロファイル消失、管理者による一部のパスワード操作などで復号不能になる可能性があります
- ファイル名、件数、サイズ、更新日時などのメタデータは暗号化されません
- `.shiro-export`はDPAPIとは別のパスフレーズ暗号化形式です。パスフレーズ紛失時は復元できません
- TTSにwin32comによるWindows SAPI5を使用しています
- ゲストモードは`chat_logs/`への履歴保存を行いませんが、メモリ、標準出力、OS側のログ、連携先APIの保存データは保護対象外です
- Biolog・家計簿APIへ送信済みのデータは会話履歴のDPAPI暗号化や保存期間管理の対象外です
- 家計簿API連携クライアントの既定接続先は`127.0.0.1:8767`です。本リポジトリには家計簿側のサーバー・DB・Docker/Compose定義を含まず、連携先環境の内部構成はこの文書では断定しません
- ループバック限定はAPI認証の代わりではなく、同一端末上の他プロセスからのアクセスを防ぐものではありません
- `diskcache` 5.6.3以下には、キャッシュディレクトリへ書き込める第三者がキャッシュ読込時に任意コードを実行できるCVE-2025-69872が報告され、修正版は公開されていません。現在のアプリコードではディスクキャッシュを有効化する`LlamaDiskCache`や`set_cache`の呼び出しを確認できませんが、利用環境の導入バージョンと有効化状況を確認してください。将来有効化する場合は専用キャッシュディレクトリを使い、書き込み権限を利用者本人に限定してください。修正版の公開後は回帰テストを行ったうえで更新してください

### 推奨事項
- Windowsアカウントを共有せず、利用者ごとに分離してください
- OSドライブとバックアップ媒体でBitLockerなどのボリューム暗号化を有効にしてください
- `chat_logs/`とバックアップ先のアクセス権限を利用者本人と必要な管理者へ限定してください
- OS再インストールやユーザープロファイル変更前に、必要な履歴を管理された保存先へ明示的にエクスポートしてください
- 保存期間を設定しても外部バックアップ、連携先API、OSログは自動削除されません。それぞれ独立した保持・削除方針を定めてください
- ゲストモードやDPAPIだけを機密情報の完全な保護策とせず、端末、アカウント、ログ、連携先、バックアップを含めて運用を評価してください
- 本アプリの導入・運営に関するリスク判断とアクセス管理は、導入・運営主体が行ってください
- 同じ`chat_logs/`を使用するShiroを複数同時に起動しないでください。同一履歴を同時保存した場合は後から保存した内容で上書きされる可能性があります
