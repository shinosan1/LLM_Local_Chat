【依頼】VRAM予測・リソース制御レイヤの実装（既存コードへの追加）

■ 目的
LLM・Whisper・TTSが同時に動作する際のVRAM不足による再ロードや性能劣化を防ぐため、
「VRAM使用量の予測・安全マージン・予約・フォールバック」を行う制御レイヤを追加する。

■ 実装順序（必須）

以下の順序で段階的にPlanを作成すること：

Step1: コアロジック実装

* リソース監視（CPU/GPU/VRAM）
* VRAM予測
* 安全マージン・予約・フォールバック
  ※ この段階では既存コードと結合しない（単体動作）

Step2: 既存LLM_Local_Chat.pyへの統合

* LLM / Whisper / TTS 呼び出し直前に制御レイヤを挿入
* UIスレッド非ブロッキングを保証

Step3: Docker環境対応

* GPU / Audio / X11 の依存確認
* 不足パッケージの洗い出し

Step4: ドキュメント更新

* README.md
* change.log

■ 成功条件（必須）

以下を満たした場合のみ「実装完了」とする：

* LLM生成中にWhisperを起動してもクラッシュしない
* VRAM使用率が高い場合にWhisperがCPUへフォールバックする
* モデルの再ロードが発生しない（ログで確認）
* UIがフリーズしない
* DEBUGログに「判断理由」が出力される
■ 追加成功条件（観測可能性）

以下のログが確認できること：

* VRAM予測値と実測値（vram_used）がDEBUGログに出力される
* フォールバック発動時に「理由（例：vram不足予測）」が明示される
* フォールバックが「発動したケース」と「発動しなかったケース」の両方が確認できる
* LLM / Whisper / TTSそれぞれの制御判断がログで追跡可能である


■ Plan出力要件

* 各Stepごとに「入力 / 処理 / 出力」を明示する
* 依存関係（どのStepがどれに依存するか）を明示する
* 不確実な点は「仮定」として明記する

■ 禁止事項

* いきなり全コードを書き始めること
* Dockerとアプリロジックを同時に変更すること

■ スコープ（必須実装）
以下の機能を既存コードに追加すること：

1. リソース監視

* CPU使用率（psutil）
* GPU使用率・VRAM使用量（pynvml優先、fallbackでnvidia-smi）
* 0.5秒周期で更新し、指数移動平均（EMA）で平滑化する

2. VRAM予測

* LLMのVRAM使用量を「モデルサイズ＋トークン数ベース」で近似する関数
* WhisperのモデルサイズごとのVRAMテーブル
* 推定関数は簡易でよいが、コメントで仮定を明示する

3. 安全マージン

* VRAMの15%を常に未使用領域として確保
* 割当判定は「空き」ではなく「安全空き」で行う

4. VRAM予約機構

* グローバルな予約カウンタを持つ
* LLM/Whisper実行前に予約を試行し、失敗時はフォールバックへ

5. フォールバック制御

* VRAM不足が予測される場合：

  * LLM：n_ctx削減、top_k低減
  * Whisper：GPU→CPU切替、model_size縮小
* 「アンロード→再ロード」は禁止（必ず回避する設計）

6. スケジューラ統合

* 既存のLLM/Whisper/TTS呼び出し直前に
  「現在の負荷＋VRAM状況」を見てポリシーを適用する層を追加

■ 制約（重要）

* 既存のUIロジックは変更しない
* Tkinterスレッドはブロックしない
* 重い初期化（モデルロード）は動的に繰り返さない
* 設定値は既存のadvanced_settings.jsonと統合するが、
  「安全制約」が常に優先される設計にする
* 過度な抽象化は禁止（可読性優先）

■ 実装方針（必ず守る）

* 「推定→判断→実行」の3層に分離する
* 瞬間値ではなくEMA値を使う
* すべての重要判断にログを出力する（DEBUGレベル）

■ 成果物

* 追加・修正した全コード（省略なし）
* 変更箇所にはコメントで「# ADDED」または「# MODIFIED」を付ける
* 主要ロジックの説明（簡潔でよい）

■ 補足
完全な精度は不要。重要なのは「破綻しないこと」と「再ロードを回避すること」。
