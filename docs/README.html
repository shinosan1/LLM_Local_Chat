LLM Local Chat

利用規約 プライバシーポリシー ライセンス 免責事項 サードパーティライセンス コード解説 SHA-256

ローカルLLM（llama.cpp）＋ Whisper音声認識＋ Windows SAPIを組み合わせた日本語AIチャットアプリです。 必要な依存ライブラリとモデルを取得済みの場合、推論・音声認識・音声合成・会話処理はローカルで実行されます。Biologと家計簿API連携は、別プロセスのローカルHTTP APIを任意で利用します。

ローカル処理を重視した構成です。機密情報を扱う業務環境へ導入する場合は、端末のアクセス制御、Windowsユーザープロファイル、ディスク暗号化、Dockerポート、依存ライブラリ、バックアップ方法を含め、組織の情報セキュリティ担当者による事前評価を行ってください。

詳しい実装の解説はコード解説を参照してください。

主な機能

  • ストリーミング表示によるリアルタイム応答
  • PyAudio + RMS-VAD + Whisper による常駐音声認識
  • Windows SAPI5（win32comによる直接制御）のTTS読み上げ
  • アバターウィンドウ（瞬き・口パクアニメーション）
  • 会話の要約メモリ（長期会話対応）
  • チャット履歴の保存・読み込み・検索
  • chat_settings.jsonによるsystem prompt・persona・応答言語等のパーソナライズ
  • TXT / MD / JSON / CSVとPNG / JPEGのチャット単位の永続添付
  • ゲストモード（chat_logs/への履歴保存なし）
  • ダークテーマUI
  • Biolog健康記録連携 — 💪ボタンで計測値・食事・活動内容・メモを入力し、確認後にBiolog APIへPOST（v1.1.0）

v1.8.0 チャット単位の保存済み添付

リリース日: 2026-08-27

TXT / MD / JSON / CSVとPNG / JPEGは、添付時点のコピーをチャットへ紐づけて保存します。同じチャットでは後続質問・チャット切替・アプリ再起動後も再添付せず参照できます。履歴JSONには復元用メタデータだけを保存し、本文・画像本体・元ファイル絶対パスは埋め込みません。

設定の「保存済み添付ファイル」では、個別削除と全チャット対象の一括削除、総件数・合計容量を確認できます。保存領域はユーザー単位に分離されないため、共有環境での一括削除は同じ保存領域を使う他利用者の添付にも影響し得ます。

system_prompt等のinline設定と外部promptは併用できます。本文なしで添付だけを送信する操作、同名・別内容の複数添付にも対応しました。

LLM GPUオフロードの再起動不要切替

生成設定では、LLM GPUオフロードの希望モードを自動・Full GPU・約75%・ 約50%・約25%・CPUから選択できます。変更時はチャットやアプリを終了せず、 旧モデルを解放してから新しい配置でバックグラウンド再読み込みします。

希望モードとは別に、最後に実際にロード成功したGPUオフロード率・配置レイヤー数・ Full/Partial/CPUを読み取り専用で表示します。自動では推論直前に最低予約量を 下回った場合だけ現在より低い配置へ自動downshiftし、同じ入力を1回だけ継続します。 推論ごとの自動upshiftは行わず、上位配置の再検討は起動・通常のモデル再読み込み・ 設定画面の「GPU配置を再評価」で行います。

家計簿の日付入力に日本語形式を追加

家計簿の日付は、従来の YYYY/MM/DD、YYYY-MM-DD、M/D に加えて、 M月D日 と YYYY年M月D日 もユーザー原文から機械抽出します。全角数字にも対応します。

入力例登録候補の日付
8月22日セリア1130円実行年を補った 2026-08-22（実行年が2026年の場合）
８月２２日セリア１１３０円同上
2026年8月22日セリア1130円2026-08-22
２０２６年８月２２日セリア１１３０円2026-08-22

実在しない日付は明示日付として採用しません。無効な年付き表現の内部を年なし形式として 再解釈することもありません。例えば、実行年が閏年でも 2025年2月29日 を 実行年の 2月29日 として採用せず、日付なしの場合と同じく実行日へフォールバックします。

「昨日」「一昨日」「先週」などの自然言語相対日付には対応していません。 日付は引き続きLLM出力ではなくユーザー原文から決定し、確認画面で修正できます。

日付直後の金額入力を修正

8/20 1603円、2026/8/20 1603円、2026-08-20 1603円のように、 日付の直後へ空白を置いて正常な金額を入力した場合も登録候補として扱います。 1 603円や12 000円のように金額の数字列自体が空白で分断された表記は、 従来どおり不正形式として拒否します。

金額直後の日本語日付入力を修正

2170円8月18日や1130円2026年8月22日のように、金額の直後へ M月D日 / YYYY年M月D日が続く自然入力も正しく扱います。数字列の単なる連結は 許可せず、実在しない月日や100円50のような表記は金額候補として採用しません。

複数取引のsource_text空白差を安全に復元

複数取引でLLMが source_text 内の半角スペースまたは全角スペースだけを 削除・追加・置換した場合、完全一致を先に試したうえで、原文上の位置が一意に 確定できるときだけ元の原文断片へ復元します。最終候補にはLLMが整形した文字列ではなく、 対応する原文の実スライスを使用します。

句読点、金額カンマ、数字、日付、店名、改行などの差は無視しません。 空白を除いた一致位置が複数ある場合や断片同士が重なる場合も、従来どおり入力全体を拒否します。

v1.7.0の主な改善

LLM Local Chat側の家計簿API連携：複数取引対応

1回の入力から最大10件の取引候補を生成できるようになりました。

これはLLM Local Chat側の候補生成・確認・API送信処理の改善です。実際の台帳登録には、別途用意したローカルのkakeibo-bridge APIが必要です。

一括登録ではありません。 「1取引 = 1確認 = 1 POST」という安全境界はそのままで、変わったのは入口だけです。候補は1件ずつ確認し、kakeibo-bridge APIへ1件ずつPOSTします。

入力: スーパーで2000円、コンビニで500円、薬局で1200円

  (1 / 3) スーパー  2,000円  → 確認 → POST #1
  (2 / 3) コンビニ    500円  → 確認 → POST #2
  (3 / 3) 薬局      1,200円  → 確認 → POST #3
項目動作
上限10件（MAX_KAKEIBO_TRANSACTIONS_PER_INPUT）
11件以上入力全体を拒否（確認画面0件・POST 0件）。先頭10件だけ処理する部分成功は行いません
金額・日付従来どおりLLM出力を最終値にせず、各取引の原文断片から機械抽出します
確認複数のときはタイトルへ (2 / 3) を表示。「この取引をスキップ」と「残りを中止」を分けています
送信直列。前のPOSTの完了を待ってから次の確認画面を開きます（並列送信はしません）
途中失敗残りの候補を処理せず停止します。このクライアントからPOST済みの取引は取り消しません
1件だけの入力従来どおりの動作・従来どおりの確認画面です

LLMが返す取引ごとの原文断片（source_text）は信用せず、原文に実在すること・空でないこと・範囲が重複しないこと・原文順に並べられることをコード側で検証します。原文に無い文言をLLMが生成した場合は候補になりません。

1つの断片に有効な金額候補が複数あり、1取引なのか内訳なのか判断できない場合は、推測せず入力全体を拒否します。

さらに、次の場合は推測せず入力全体を拒否します（意図しない部分送信を防ぐため）。

状況例動作
LLMが取引を取りこぼした原文に3取引あるのにLLMが2件しか返さない全体拒否。原文の金額をすべての断片が覆っているかを確認します
金額だけの断片「スーパーで2000円と500円」を「スーパーで2000円」「500円」へ分割全体拒否。同一文脈内の複数金額を人工的に切り分けたものは受理しません
日付が一意に決まらない「8/16 スーパーで2000円、8/17 コンビニで500円、薬局で1200円」全体拒否。薬局がどちらの日付か確定できません

日付は、原文全体の明示日付がちょうど1種類のときだけ、日付を持たない取引へ適用します。「8/16 スーパーで2000円、コンビニで500円」なら両方 8/16 です。

確認・POSTシーケンスが進行中の間は、キーボード入力・音声入力とも新しい送信を開始しません（Controller.is_busy()）。完了・スキップ・中止・エラーのいずれでも解除されます。

音声入力とキーボード入力は同じ経路を通るため、どちらでも同じ処理になります。

v1.5系の主な改善

暗号化インポート／エクスポート

別PCや別のWindowsユーザー環境へ会話履歴を移行するため、パスフレーズ付きの暗号化形式.shiro-exportを追加しました。

通常の会話履歴は、これまでどおり現在のWindowsユーザーに紐づくDPAPIで暗号化して保存します。.shiro-exportは、DPAPI履歴を別環境へ移すための持ち運び用形式です。

暗号化には以下を使用します。

  • scryptによるパスフレーズからの鍵導出
  • AES-256-GCMによる認証付き暗号化
  • 暗号設定を含む外側ヘッダーのAAD認証
  • 毎回新しく生成されるsaltとnonce

パスフレーズ、暗号鍵、復号済みの会話履歴は、設定ファイルやログへ保存しません。暗号化・復号時にも平文の一時ファイルは作成しません。

エクスポート対象

暗号化エクスポートの対象は、DPAPIでディスクへ保存済みの会話履歴だけです。

以下はエクスポートできません。

  • ゲストモードの会話
  • まだ保存されていない会話
  • 保存後にメモリ上で追加・変更された未保存部分
  • 保存済み添付の実体と添付メタデータ

.shiro-exportをインポートしても添付は復元されません。この形式は会話履歴の持ち運び用であり、添付ファイルのバックアップではありません。

「現在の会話のみ」を選択した場合も、保存済みの履歴をディスクから読み直してエクスポートします。

インポート処理

.shiro-exportをインポートすると、パスフレーズで復号した後、現在のWindowsユーザー用DPAPIで再暗号化してchat_logsへ保存します。

保存前に以下を確認します。

  • ファイル形式とバージョン
  • scrypt、salt、nonce、AES-GCM設定
  • 暗号文の改ざん
  • 復号後の履歴形式
  • 会話件数、文字数、入れ子、ファイルサイズなどの上限
  • 既存履歴との重複
  • 履歴の保存期間

すべての履歴を検証してから保存を開始し、通常の書き込みエラーが発生した場合は、今回追加した履歴を巻き戻します。既存の履歴は変更・上書きしません。

重複する会話は、スキップするか複製としてインポートするかを選択できます。

注意事項

  • .shiro-exportのパスフレーズを忘れた場合、履歴を復旧できません。
  • 弱いパスフレーズは、暗号化ファイルを取得した第三者によるオフライン解析を受ける可能性があります。
  • 暗号化ファイルとパスフレーズを同じ場所へ保存しないでください。
  • 通常のDPAPI履歴は、別PCや別のWindowsユーザーでは復号できない可能性があります。
  • クラウドストレージなど保存先自体の安全性を、本アプリが保証するものではありません。

  • 現在の保存済み会話をエクスポート

起動できない場合の復旧手順

会話履歴の復号・形式確認・移行に失敗した場合、Shiroは履歴を自動削除・自動移動せず、通常起動を中止します。

  1. 元のWindowsユーザーと元のPC環境で起動しているか確認します。DPAPI暗号文は別ユーザーや別環境では復号できない場合があります。
  2. 旧版を含むすべてのShiroを終了し、chat_logs/と対象ファイルのバックアップを確保します。バックアップはアクセス制限された場所に保存し、公開リポジトリや共有クラウドへ置かないでください。
  3. 破損・未対応と表示されたファイルがある場合は、削除せず、chat_logs/外の安全な非公開フォルダへ手動で退避してから再起動します。退避した履歴は一覧に表示されなくなります。
  4. .history_migration.lockが残っている場合は、すべてのShiroが終了していることを確認した場合に限り、chat_logs/.history_migration.lockを手動で削除して再起動します。Shiroの実行中は削除しないでください。
  5. 「Windows DPAPIを利用できません」と表示された場合は、同梱の依存関係とpywin32が利用できるPython環境で起動してください。

初回移行中は旧版Shiroを同時起動しないでください。ロックファイルはv1.4.2同士の移行を調整するもので、旧版による平文履歴の新規保存までは防げません。

暗号化後の履歴はv1.4.1以前では読み込めません。別PC・別Windowsユーザーへ移す場合は、ファイルメニューの「暗号化エクスポート」を使用してください。

暗号化インポート／エクスポート

.shiro-exportは、scryptでパスフレーズから鍵を導出し、AES-256-GCMで会話履歴とメタデータを認証付き暗号化する持ち運び用形式です。通常のchat_logs/はWindows DPAPI、持ち運び用ファイルはパスフレーズ暗号化という役割分担です。

  • パスフレーズは設定・履歴・ログへ保存されません。紛失した場合は復元できません
  • 出力は人間が直接読めるテキストではありません
  • 復号した平文を一時ファイルへ保存せず、メモリ内で検証します
  • インポート後は現在のWindowsユーザー用DPAPIで再暗号化します
  • 暗号化ファイルとパスフレーズを同じ場所へ保管しないでください
  • Python上の平文・鍵をメモリから完全消去できるとは保証しません
  • 通常の書込例外では追加ファイルを巻き戻しますが、停電・OS停止に対する完全なトランザクション保証はありません
  • 既存の平文.txtはインポート対象ではなく、アプリが自動削除することもありません

音声入力について

音声入力は周囲の音（テレビ・エアコン・会話等）を拾うことがあります。 これにより意図しない発話が送信されるハルシネーションが発生する場合があります。

対処方法：

  • メニューの「設定」から音声検出感度（RMS閾値）の数値を上げることで改善できます
  • デフォルト値は150です。200〜300程度に上げると誤検知が減少します
  • 数値が大きいほど感度が低くなります（静かな環境では小さい値を推奨）
  • 使用しないときはマイクボタンをクリックしてOFFにしてください

免責事項

  • 本アプリはAIの回答精度を保証しません
  • 音声認識の誤認識・ハルシネーションにより意図しない操作が行われる場合があります
  • 重要な情報は必ずご自身で確認してください

6. モデルを設定する

chat_settings.jsonがない場合も、アプリはコード既定値で起動を試みます。既定のモデルが見つからない場合は読込エラーが表示されますが、メイン画面の「ファイル」→「設定」を開き、「参照」ボタンから用意したGGUFモデルを選択して適用できます。保存した設定はchat_settings.jsonへ記録されます。

起動前に手動設定したい場合だけ、chat_settings.json.exampleをchat_settings.jsonへコピーし、model_pathなどを編集してください。

パーソナライズとVisionは、設定画面ではなくchat_settings.jsonで設定します。既存の設定ファイルに次のキーがなくても従来どおり起動します。

{
  "system_prompt": "",
  "user_personalization": "",
  "response_language": "回答は必ず日本語のみで行ってください。",
  "reasoning_visibility_instruction": "内部の思考過程、分析、推論、計画は表示せず、ユーザーに見せる最終回答だけを出力してください。",
  "external_prompt_files": {
    "system_prompt": "prompts/system.md",
    "user_personalization": "",
    "user_profile": "prompts/profile.txt",
    "instructions": []
  },
  "vision_enabled": false,
  "vision_handler": "gemma4",
  "vision_projector_path": ""
}

外部promptはUTF-8の.txt / .mdに対応し、相対パスはアプリ配置フォルダ基準です。inline system → external system → inline personalization → external personalization → response language → reasoning visibility → external profile/instructionsの順で併用し、完全に同一の文章と同一ファイルだけを重複挿入しません。外部promptの欠損・形式・文字コード・サイズのエラーは警告を表示し、inline設定を含む読める設定だけで起動を継続します。

Visionを使う場合は、現在のllama-cpp-python 0.3.34で利用できるgemma4またはllava15を指定し、対象モデルに対応するprojector / mmproj GGUFをvision_projector_pathへ設定してください。vision_enabledの既定値はfalseです。

.\.venv\Scripts\python.exe LLM_Local_Chat.py

使い方

基本操作

起動するとメインウィンドウとアバターウィンドウが開きます。 ステータスバーが「✅ 待機中」になったらチャット可能です。

テキスト入力欄にメッセージを入力して Enter キーまたは「送信」ボタンで送信します。 Shift + Enter で改行できます。

ファイル添付

入力欄上の「📎 ファイルを添付」から、TXT / MD / JSON / CSVまたはPNG / JPEGを選択できます。本文あり・添付あり、本文だけ、添付だけのいずれも送信できます。本文も添付もない場合は送信しません。添付は通常チャットだけで使用でき、最大8件、画像はそのうち1枚までです。同名でも内容が異なるファイルは内部IDで区別し、data.csv、data.csv (2)のように表示します。

添付時点の内容はchat_logs/attachments/<session-id>/以下のアプリ管理領域へ、元ファイル名ではなく内部IDを使ってコピーします。送信後も「チャット添付: ファイル名」の表示が残り、「続けてください」などの後続質問へ同じ内容を1ターン内で重複させず再投入します。新しいチャットを開始しても元チャットの添付は削除されず、別チャットを開けばそのチャット固有の添付へ切り替わります。保存済みチャットを再読込したときとアプリ再起動後にも復元します。

保存済み添付は元ファイルとは別コピーです。元ファイルを編集・移動・改名・削除しても自動更新されません。最新版を使う場合は、現在チャットの古い添付を解除して再添付してください。添付は重要ファイルのバックアップシステムではなく、アプリ内添付を唯一の保存場所として利用しないでください。

入力欄の「添付解除」は、確認ダイアログで同意した場合に、現在のチャットに紐づくすべての添付と対応するアプリ管理領域のコピーを削除します。会話本文とAI回答、元ファイル、別チャットの添付は削除しません。チャット自体を削除した場合は、そのチャット専用の添付も内部ID・セッションIDで削除します。削除した添付は過去チャットから再参照できず、アプリによる復元は保証されません。

保存管理の操作経路は、ファイル → 設定 → 保存済み添付ファイル → 選択した添付を削除または保存済み添付ファイルをすべて削除です。一覧ではファイル名、種類、サイズ、紐づくチャット、状態、総件数、合計容量を確認できます。一括削除は現在のアプリ保存領域で管理される全チャットの保存済み添付が対象で、通常の会話履歴は残ります。部分失敗時は成功・失敗・スキップ・再試行待ち件数を表示し、完了していないのに「すべて削除しました」とは表示しません。

履歴JSONへ直接保存するのは、内部ID、basename、種類、サイズ、SHA-256等の復元用メタデータだけです。元ファイル絶対パス、TXT / MD / JSON / CSV本文、画像bytes、base64、data URIは埋め込みません。ただし、LLMが添付内容やファイル名を回答へ引用・要約した場合、そのAI回答は通常の会話履歴として保存され、後の要約メモリにも含まれる可能性があります。

本アプリはユーザーアカウント単位の添付分離・認証・権限管理を提供しません。同じWindowsアカウント、同一PC、共有フォルダ等で同じアプリデータ保存領域を複数人が使用する場合、一括削除はその保存領域を利用する他のユーザーを含む全チャット添付へ影響する可能性があります。Windowsの別ユーザーであっても同じ保存先を共有する場合は、ユーザー単位の保護を保証しません。ローカルLLMであることだけで、PCへの不正アクセス、マルウェア、同一アカウントの別利用者、アクセス権を持つプロセスから完全に安全になるわけではありません。

個人情報、業務機密、パスワード、APIキー、アクセストークン、秘密鍵等を含むファイルは不用意に添付しないでください。TXT / MD / JSON / CSV内のPowerShell、shell、Python、JavaScript等は自動実行せず、LLMへの入力データとして扱います。一方、文書内の「これまでの指示を無視してください」のような文章がprompt injectionとして回答へ影響する可能性はあります。外部から取得した文書を信頼できる命令として扱わず、生成結果を確認せず重要な操作へ利用しないでください。拡張子、UTF-8、ファイルサイズ、画像形式・画素数の検査は異常入力の影響を抑える制限であり、ファイルや回答の安全性を完全には保証しません。

テキストは1ファイル1MiB、画像は1ファイル10MiBかつ16メガピクセル以下です。上限超過やUTF-8で読めないテキストは切り捨てずに拒否します。添付がある間は、system prompt・要約・全会話履歴・添付・新規入力・応答予約を合わせてcontextへ収まらない場合、履歴を黙って省略せず警告します。画像入力では4,096画像トークンを事前予約しますが、モデル固有の実トークン数を送信前に完全保証できないため、実行時にcontext超過として拒否される場合があります。

保存済み添付はアプリ終了後も残るため、画像や多数の添付を使い続けるとディスク使用量が増えます。自動期限削除、自動容量削減、ごみ箱、自動バックアップ、添付暗号化は提供しません。設定画面の件数・合計容量・個別削除・一括削除を使って管理してください。実体欠損、読込不能、サイズ不一致、保存済みSHA-256との不一致を検出した添付はLLMへ渡さず、警告します。

.shiro-exportには添付実体も添付メタデータも含まれません。インポート後のチャットへ添付は復元されないため、.shiro-exportを添付ファイルのバックアップとして使用しないでください。

音声入力

コード上の既定値とchat_settings.json.exampleでは、起動時のマイク・TTS読み上げはともにOFFです。「ファイル」→「設定」で次回起動時の状態を変更できます。 マイクボタンをクリックするとONになります。 ONの状態で一定以上の音量を検知すると自動的に録音を開始し、Whisperで文字起こしして送信します。 再度クリックするとOFFに戻ります。

起動時マイクを有効にする設定とWhisper実行モードは、次回起動時に反映されます。初回のWhisperダウンロード・ロードには時間がかかる場合があります。
TTS読み上げ中はハウリング防止のため音声入力が自動的に抑制されます。

TTS（読み上げ）

AIの返答をWindows SAPIで読み上げます。起動時はOFFがデフォルトです。 メニューからTTSのON/OFFを切り替えられます。 読み上げ中は「停止」ボタンで中断できます（タイミングによっては中断できない場合があります）。

健康記録モード（Biolog連携） — v1.1.0

💪ボタンをクリックすると健康記録モードがONになります。 このモードでは、計測値・食事・活動内容・メモを話しかけると、確認後にBiolog APIへデータをPOSTします。食事ログ、行動ログ、メモだけの登録にも対応します。

入力例：

体重65kg、体脂肪20%、朝はオートミールを食べた

動作結果：

  • チャットに「✅ Biolog記録: 2026-05-06 体重 65.0kg 食事:朝はオートミールを食べた」と表示
  • Biologの健康記録へ保存

事前準備： Biolog側の文書とComposeを確認してAPIを起動し、LLM Local Chatを実行するPCからヘルスチェックへ接続できることを確認してください。 標準ComposeではBiolog APIを127.0.0.1:8766に限定して公開します。

curl http://localhost:8766/api/health/health

環境変数でエンドポイントを変更できます：

$env:BIOLOG_URL = "http://localhost:8766"  # デフォルト
.\.venv\Scripts\python.exe LLM_Local_Chat.py

計測値・食事ログ・行動ログ・メモがすべて空の場合だけ送信しません。食事ログ・行動ログ・メモを明示した入力は、ユーザー原文から決定的に解析されます。

ゲストモード

「ゲストモード: OFF」ボタンをクリックするとゲストモードがONになります。 ゲストモードがONのとき、会話履歴はchat_logs/へ自動保存されず、ゲスト会話を暗号化エクスポートすることもできません。ただし、実行中のメモリ、標準出力やOS側のログ、連携先APIへ送信したデータまで消去・保護する機能ではありません。 プライベートな会話や一時的な用途に使用してください。 再度クリックすると通常モードに戻り、新しいセッションが開始されます。

チャット履歴

左ペインに過去の会話一覧が表示されます。クリックで読み込めます。 上部の検索欄でタイトル・要約の部分一致検索ができます。 右クリックで個別削除が可能です。 履歴はアプリ配置フォルダ内のchat_logs/へ、DPAPI暗号化されたJSONエンベロープとして保存されます。ファイル名、件数、サイズ、更新日時は暗号化されません。 設定画面で保存期間を選択できます。有限期間を初めて適用するときは削除候補件数を表示し、確認後すぐに削除します。外部バックアップは自動削除されないため、バックアップ側の保持期間も別途管理してください。

よくある質問

Q. OllamaやLM Studioを使わないのはなぜですか？ A. llama.cppをPythonバインディング（llama-cpp-python）から直接呼び出し、LLM推論をローカルで実行するためです。必要な依存ライブラリとモデルを取得済みで、オプションのBiolog・家計簿API連携も別プロセスのローカルAPIへ限定した構成では、通常の会話処理に外部のLLMサービスを使用しません。セットアップ、モデル取得、外部リンクの閲覧にはインターネット接続が必要です。

Q. CPUだけでも動きますか？ A. CPU実行へフォールバックできます。CPU専用PCでは、セットアップ時にrequirements-cpu.txtを使用してください。応答速度はモデルサイズ、量子化形式、CPU、メモリ帯域、コンテキスト長などに大きく依存し、実用的な速度になるとは一律に保証できません。

Q. Whisperのモデルは自動でダウンロードされますか？ A. 起動時マイクを有効にした場合、初回ロード時にWhisperモデルが自動的にダウンロードされます。マイク無効時は、TTSが有効でもWhisperをロードしません。

Q. TTSには何を使用していますか？ A. win32com.client.Dispatch("SAPI.SpVoice") により、Windows SAPI5をワーカースレッドから直接制御しています。

確認済みの範囲

  • LLM推論、Whisper音声認識、Windows SAPI5による音声合成はローカルプロセスで実行されます
  • 現在のアプリコードでは、外部のLLM APIへ会話内容を送信する処理は確認できません
  • Biolog・家計簿API連携は別プロセスのHTTP APIを使用します。現在のアプリコードでは接続先をループバックアドレスに制限し、環境プロキシを使用せずに接続します。家計簿アプリ、DB、kakeibo-bridgeサーバーは本リポジトリに含まれず、実際に利用できるかどうかは別途用意したローカルAPIの稼働・ネットワーク設定にも依存します

⚠️ 使用するモデルについての注意：
GGUFモデルファイル自体が独立して通信や攻撃を行うものではありません。ただし、信頼できない、または破損したファイルがモデル読み込みライブラリの脆弱性を突く可能性があります。信頼できる配布元から取得し、llama.cppおよびllama-cpp-pythonを定期的に更新してください。モデルの仕様・ライセンスも確認してください。

導入・運営前に確認すべき点

  • 会話履歴はWindows DPAPIの現在ユーザースコープで暗号化されます。暗号化は同一Windowsユーザーとして動作する別プロセスやマルウェア、実行中メモリ、画面、クリップボード、標準出力を保護しません
  • 暗号文は原則として同じWindowsユーザープロファイルと当該Windows環境に依存します。OS再インストール、プロファイル消失、管理者による一部のパスワード操作などで復号不能になる可能性があります
  • ファイル名、件数、サイズ、更新日時などのメタデータは暗号化されません
  • .shiro-exportはDPAPIとは別のパスフレーズ暗号化形式です。パスフレーズ紛失時は復元できません
  • TTSにwin32comによるWindows SAPI5を使用しています
  • ゲストモードはchat_logs/への履歴保存を行いませんが、メモリ、標準出力、OS側のログ、連携先APIの保存データは保護対象外です
  • Biolog・家計簿APIへ送信済みのデータは会話履歴のDPAPI暗号化や保存期間管理の対象外です
  • 家計簿API連携クライアントの既定接続先は127.0.0.1:8767です。本リポジトリには家計簿側のサーバー・DB・Docker/Compose定義を含まず、連携先環境の内部構成はこの文書では断定しません
  • ループバック限定はAPI認証の代わりではなく、同一端末上の他プロセスからのアクセスを防ぐものではありません
  • diskcache 5.6.3以下には、キャッシュディレクトリへ書き込める第三者がキャッシュ読込時に任意コードを実行できるCVE-2025-69872が報告され、修正版は公開されていません。現在のアプリコードではディスクキャッシュを有効化するLlamaDiskCacheやset_cacheの呼び出しを確認できませんが、利用環境の導入バージョンと有効化状況を確認してください。将来有効化する場合は専用キャッシュディレクトリを使い、書き込み権限を利用者本人に限定してください。修正版の公開後は回帰テストを行ったうえで更新してください
